# Source Gathering Spec

## Purpose

Source gathering should make Tweenverse auditable. A user should understand why each provider was searched, why each source was selected, how strong that source is, and what part of the run it supports.

This is not a generic source browser. It is the evidence layer for a synthetic audience simulation.

## Current State

The app already retrieves from Wikipedia, Google News RSS, Reddit, Vie publique, and data.gouv.fr. It records provider outcomes and source cards, and context packs carry `supportingSourceIds`.

The missing product layer is explanation. Users can see sources, but they cannot yet see the path from prompt to provider selection to source selection to downstream claims.

## Claim Types

Use three labels throughout evidence and reporting:

- `Observed`: directly present in an external source or measured dataset. Examples: a published policy date, a survey topline, a TV audience actual, an official dataset value.
- `Simulated`: generated by Tweenverse personas or aggregation. Examples: persona quotes, stance distribution, simulated TV viewing choice.
- `Inferred`: concluded by Tweenverse by connecting observed context and simulated outputs. Example: cost-sensitive households may react more strongly because official economic indicators are weak and the selected personas have high economic vulnerability.

UI labels should be plain:

- `Observed source`
- `Simulated response`
- `Analyst inference`

## UX

The Lab should expose an `Evidence trace` section with:

- query plan: selected providers, query text, trigger terms, and reason;
- provider diagnostics: success, fallback, blocked, rate-limited, or parse failure;
- source cards: title, provenance, source name, snippet, score breakdown, selection rationale, limits, and supported claim type;
- source influence: first through source support labels, later through context-pack and decision-report links.

The default view should remain compact. Numerical score breakdowns can be visible but secondary to plain-language reasons.

## Data Contract

Add these structures beside existing retrieval output:

- `RetrievalPlan`: input terms, provider decisions, skipped providers, and query variants.
- `ProviderDecision`: provider, query, reason, trigger terms, and confidence.
- `SourceSelectionExplanation`: source ID, score breakdown, selected-because reasons, limitations, and supports.
- `EvidenceClaim`: claim type, text, source IDs, related run artifact IDs, and confidence.

Old runs should remain readable, so new fields should be optional or defaulted by schema parsing.

## Implementation Plan

1. Extend shared schemas in `src/lib/labSchemas.ts`.
2. Generate a retrieval plan in `src/server/lab/retrieval.ts`.
3. Produce source explanations and observed evidence claims after provider retrieval.
4. Update the Lab source section into an evidence trace.
5. Add tests for query-plan metadata, source explanations, and claim labels.
6. Later, attach inferred and simulated claims from context packs, reactions, aggregation, validation, and the Decision Report.

## Acceptance Criteria

- A user can explain why each provider was searched.
- A user can explain why every returned source was selected.
- Fallback sources are explicit and carry limits.
- Reddit is labeled as public-discourse evidence, not representative evidence.
- Official sources are labeled as official observed context.
- Source metadata is available in the API response, not only rendered in the UI.
- Existing retrieval behavior and provider calls continue to work.

## Risks

- Too much evidence metadata can make the app feel defensive. Keep the default wording short.
- Numeric scores can imply false precision. Pair scores with plain rationale and limitations.
- Inferred claims require careful follow-through in Decision Report; first release should create observed source claims and reserve simulated/inferred labels for downstream artifacts.
